# Exploration: One SEO API for the document head

**Status:** built in part
**Created:** 2026-11-17
**Author:** Claude, for the project owner
**Context:** A contracts-first SEO API that owns a page's search-facing output, phase 1 of which (title, description, robots, canonical) was built.
**Approved by:** the project owner on 2026-11-17
**Socialized with:** not socialized

---

## Problem Statement

SEO plugins each bring their own model of a page's head, and those models do not agree. The [search engine research](2026-11-17-search-engine-requirements.md) found that engines ask for little, and what hurts a site is its own outputs disagreeing: a canonical link that differs from the sitemap entry, the `og:url` or the structured data URL. Plugin authors had no shared place to read or change the canonical URL, robots directives or title. Sites had no meta description, social tags or structured data at all.

## Current State

- In wordpress-develop, head output came from unrelated functions in at least eight packages: `wp-theme`, `wp-route`, `wp-query`, `wp-support`, `wp-sitemap`, `wp-rest-api`, `wp-customizer` and `wp-deprecated`.
- Each was hooked separately from `wp-plugin-legacy`'s `default-filters.php`.
- `wp_get_document_title`, `_wp_render_title_tag`, `wp_robots` and its helpers, `wp_get_canonical_url` and `rel_canonical` lived in `wp-theme-legacy`.
- `X-Robots-Tag` headers were sent by hard-coded `header()` calls in three packages.
- The packages did not boot a site yet. `src/wp-includes/` was empty and nothing called any package's `ServiceProvider`. The project owner confirmed that packages are built and tested standalone.
- The existing service containers (`HookServiceContainer`, `OptionServiceContainer`) are `final`, have no `has()`, and keep stale instances after a late `add()`. One references the wrong class for its own singleton.

## Proposed Solution

Domain-Driven Design layers as separate Composer packages under `wp-seo`. All contracts live in one domain package. Each contract is bound on its own in a container, so one binding or a whole layer can be swapped.

### Architecture

```
                     wp-seo-domain
          (contracts, value objects, SeoServiceContainer)
            ^        ^          ^           ^          ^
            |        |          |           |          |
      wp-seo-app  wp-seo-   wp-seo-     wp-seo-    wp-seo-contract-
      (use cases) infra-wp  infra-memory legacy     tests (Pest)
                  (WP hooks,            (old WP functions,
                   filters)              wrappers via container)

 legacy requires virtual packages:
   speedyspec/wp-seo-app-implementation   <- provided by wp-seo-app
   speedyspec/wp-seo-infra-implementation <- provided by each infra package

 request: PageContextProvider -> resolvers (title, description,
          robots, canonical) -> head contributors -> HeadDocument
          -> HeadRenderer -> HTML
```

- `wp-seo-domain` requires only PHP and calls no WordPress function. No class in it is `final`.
- `wp-seo-app` requires only the domain. Infrastructure packages never require each other.
- WordPress filters appear only in `wp-seo-infra-wp`. The app layer holds plain resolvers for non-WordPress hosts.
- `wp-seo-presentation` (REST) and `wp-seo-indexnow` are later phases.

### Data Model

- `Url`: absolute, `http` or `https`, with a host.
- `RobotsDirectives`: an ordered, immutable map of name to `true` or a string. Names are an open set; `noarchive`, `nocache` and `nosnippet` stay distinct.
- `PageContext`: kind (singular, front page, archives, search, not found, other), object type and id, page number, locale, HTTP status.
- `MetaTag` with a `name` or `property` attribute; `LinkTag`; `HeadDocument`; `SeoOverrides` (title, description, canonical, robots, image per object).

### Interfaces

- Resolvers: `CanonicalUrlResolverInterface::resolve(PageContext): ?Url`, `TitleResolverInterface::resolve(PageContext): string`, `DescriptionResolverInterface::resolve(PageContext): ?string`, `RobotsDirectivesResolverInterface::resolve(PageContext): RobotsDirectives`.
- Sources: `PageContextProviderInterface`, `PermalinkSourceInterface`, `SiteInfoProviderInterface`, `ContentSourceInterface`, `SeoOverridesRepositoryInterface`.
- Head: `HeadContributorInterface::contribute(HeadDocument, PageContext)`, a contributor registry ordered by priority, `HeadDocumentBuilderInterface::build(PageContext)`, `HeadRendererInterface`.
- Edges: `ResponseHeaderEmitterInterface`, `EventDispatcherInterface` (`dispatch`, `filter`).
- `SeoServiceContainer`: `add`, `remove`, `extend`, `has`, `get`. A change after a contract was resolved throws.
- Three contracts were added during planning: site info, content source and head document builder. `extend()` and `PageContext::hasPost()` came during the build.

## Design Decisions

1. **Contracts in their own package; implementations replaceable in part or whole.** The project owner ruled this. One container binding per contract gives partial replacement; virtual packages let Composer refuse an install with a layer missing while any vendor can supply it.
   *Trade-off:* six packages for phase 1, and stricter rules than the existing `wp-option` packages.
2. **Use cases live in `wp-seo-app`, not the domain.** The designer's call, so the contracts package holds no behaviour.
   *Trade-off:* one more package to install.
3. **Write a new container, not copy the old ones.** A late `add()` for a resolved contract throws instead of silently keeping the stale instance.
   *Trade-off:* plugins must bind before first use.
4. **Existing functions and filters keep working.** The moved functions become wrappers. `pre_get_document_title`, `document_title_parts`, `wp_robots`, `get_canonical_url` and the rest fire with the same arguments. Robots defaults stay as `wp_robots` callbacks, so `remove_filter()` still works.
   *Trade-off:* under WordPress, title and robots reproduce WordPress's algorithms and ignore overrides.
5. **Each legacy function resolves only its own part, at its own hook time.** An eager, cached build of the whole head was tried and changed when and how often filters fired. The spec was amended after the final review of phase 1.
   *Trade-off:* one head document for the whole page waits for a later phase.
6. **No new output in phase 1 except the meta description.** `wp_seo_render_head()` on `wp_head` prints only tags no legacy function prints. Canonical stays singular-only.
   *Trade-off:* canonical on archives waits for phase 3.
7. **Titles and descriptions are display text.** Every output escapes without double-encoding.
   *Trade-off:* a `pre_get_document_title` filter returning raw `<`, `&` or quotes now gets them encoded.
8. **Behaviour follows the research.** No length limits, no meta keywords, `max-image-preview:large` by default on public pages. Sitemaps and robots.txt in phase 3 follow [ADR-012](../../adr/012-redirects-sitemaps-robots-feeds.md).
   *Trade-off:* none recorded.

## Implementation Phases

1. **Contracts and the head core.** Domain, app, both infra packages, legacy and contract tests; resolvers for context, canonical, title, description and robots; head rendering; legacy wrappers.
   *Delivers:* a meta description for the first time. **Shipped:** built on branch `feat/wp-seo-phase-1` on 2026-11-17, then moved to SpeedySpec/speedyspec-api-seo, whose first package commit is dated 2026-11-18.
2. **Structured data and social cards.** Schema pieces, `@id` factory, graph builder, social card resolver, a 1200x630 image size. *Delivers:* one JSON-LD graph and Open Graph. Not started.
3. **robots.txt, sitemaps, hreflang.** *Delivers:* builder with free-form lines; sitemaps with honest `lastmod`. Not started.
4. **Redirects and the URL-changed event.** *Delivers:* redirect store and one change event. Not started.
5. **Extensions and admin.** IndexNow, verification registry, crawler catalogue, REST endpoints, the SEO screen in the static admin. Not started.

Phases 2 to 5 each need a short design addendum before planning.

## Fleet Impact

- **wordpress-develop:** the phase 1 work moved functions out of `wp-theme-legacy`, deleted its `robots-template.php`, and added the `wp_seo_render_head` hook line to `default-filters.php`. Confirmed in git history.
- **SpeedySpec/speedyspec-api-seo:** the wp-seo packages moved here (commit "move the wp-seo packages", 2026-11-17). Confirmed with `gh`.
- **Static admin and admin backend:** affected only in phase 5. Unverified.
- No package requires `wp-seo-legacy` yet, so no running site uses it.

## Open Questions

1. **Can the site boot from the packages?** — `src/wp-settings.php` still requires the deleted `robots-template.php`, and nothing requires `wp-seo-legacy`. Settled by the site-wide package wiring.
2. **Are URLs normalised before `og:url` ships?** — `Url` accepts whitespace and control characters and compares raw strings. Fix before phase 2.
3. **Can a `name` and a `property` tag share a key?** — `HeadDocument` keys meta by key alone, so they overwrite each other. Fix before phase 2.
4. **How are overrides stored, and who may set a canonical or `noindex`?** — empty-string overrides, storage keys, and WordPress title and robots ignoring overrides. Settled with phase 5.
5. **How is `unavailable_after` kept?** — robots values containing a comma are dropped.
6. **Does the site use HTTPS, or only this request?** — `usesHttps()` reads `is_ssl()`.
7. **Does the container need a circular-dependency guard?** — none exists in `get()`.
8. **Research items** — Bing's `noarchive`/`nocache` wording (not blocking), Google's AI-preference robots.txt syntax (before phase 3), and X card rules (before phase 5).

## Success Criteria

- [x] Every contract replaceable alone — container tests replace one binding and check the rest are untouched.
- [x] A late replacement throws — container tests for `add`, `remove` and `extend` after `get`.
- [x] Legacy output byte-identical to WordPress for title, robots and canonical — legacy wrapper tests.
- [x] Garbage from legacy filters drops the tag, never fails the page — infra-wp resolver tests.
- [x] Nothing bound prints nothing, with no fatal error — legacy tests.
- [x] No description tag for empty or tag-only content — resolver and renderer tests.
- [x] Legacy code names no implementation package — a source scan test.
- [ ] Passing `tests/phpunit` on a running site — out of scope until wiring.

## Non-Goals

- **Content scoring and readability** — what SEO plugins add on top.
- **Core Web Vitals** — set by themes and assets.
- **Content-type rich results (Product, Event, Recipe, JobPosting)** — need plugin data.
- **llms.txt, meta keywords, sitemap `priority`/`changefreq`/pings, FAQ, HowTo, SearchAction, AMP** — no engine reads them.
- **Blocking AI crawlers** — host and CDN work.

## Alternatives Considered

### Option: One `wp-seo` package with contracts and implementation
- **Pros:** simplest.
- **Cons:** contracts not separate; implementations not replaceable.
- **Verdict:** Rejected by the project owner.

### Option: One package per capability, each with its own contracts
- **Pros:** clean boundaries.
- **Cons:** shared value objects and the canonical resolver need yet another package; agreement becomes a coordination problem.
- **Verdict:** Rejected.

### Option: Plain hooks beside the existing functions
- **Pros:** cheapest.
- **Cons:** nothing gets a single view of the page.
- **Verdict:** Rejected.
