# SpeedySpec Guide site Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Astro site of `speedyspec-guide`: a standalone WordPress API section and a SpeedySpec API section, both by seam. Pages have the approved layout (seam rail, relationship panel, tested examples, verdicts), seam diagrams are drawn in Mermaid with circular dependencies in red, and search finds a function by its WordPress name. Everything is built from the data plans 1 and 2 produce.

**Architecture:** A new workspace package `site/` (Astro 5, static output, MDX). It never reads files directly in its pages. A read model in `site/src/model/` loads the guide's data once, through one `GuideData` loader (generated JSON, `seams/*/seam.yaml`, example files, and the `content/` MDX collection), and turns it into plain view objects (`SeamView`, `SymbolView`, `SpeedySpecView`) with pure, unit-tested functions. Astro components only render view objects. Mermaid text is generated by pure functions and rendered to SVG at build time.

**Tech Stack:** Astro 5 with `@astrojs/mdx`; `mermaid-isomorphic` (build-time Mermaid, Playwright Chromium); `rehype-mermaid` for diagrams written in MDX; Pagefind; plain CSS with custom properties (no Tailwind, no client framework); Bun for tests (`bun test`, `HTMLRewriter` for assertions on built HTML).

**Spec:** `docs/superpowers/specs/2026-11-20-speedyspec-guide-design.md` (sections "Information architecture", "Seams", "Pages", "Evidence", "History"). The approved mockup is `.superpowers/brainstorm/81581-1795221671/content/examples-v3.html` in `wordpress-develop`.

Plan 3 of 4. It builds on plans 1 and 2, both merged on `main` in `packages/speedyspec-guide`.

## Global Constraints

- Static output only; no client-side framework. The only browser JavaScript is Pagefind's search UI.
- Pages describe exactly what the data says. A page never invents a verdict, an edge, a version or an example result. When data is missing, the page says so ("not yet documented", "not run", "unreleased").
- WordPress pages are readable on their own. Each one carries only the verdict pill and the short "On SpeedySpec" box about SpeedySpec.
- Diagrams are Mermaid, rendered to SVG at build time, light and dark (`<picture>` with `prefers-color-scheme`). A circular dependency is red **and** labelled "circular", in diagrams and in chips and lists alike. Hook links are dashed.
- Light and dark follow `prefers-color-scheme`. Concise and quiet: one content column, no banners.
- The site reads generated data from `GUIDE_DATA_DIR` (default the repo's `generated/`), seams from `GUIDE_SEAMS_DIR` (default `seams/`) and content from `GUIDE_CONTENT_DIR` (default `content/`). The build tests use fixtures through these.
- The design principles apply. The read model depends on `@speedyspec-guide/domain` only. Loading is one adapter (`GuideData`).
- Commit locally only. Don't commit `docs/superpowers` plans or specs.

## Review Focus

- A symbol id with characters URLs can't hold: namespaces (`WpOrg\Requests\Exception`), dynamic hook names (`pre_option_{$option}`, `{$meta_type}_{$args['type']}`), methods (`WP_Hook::apply_filters`). Each must get one stable, unique slug, and two ids must never collide. Task 2 covers it.
- A seam with no members yet, a symbol with no content page, a symbol with no examples, and an example with no results file must each build a page that says so, not crash the build. Tasks 6 and 7 cover them.
- Mermaid labels containing `{`, `}`, `$`, `"`, `::` or `\` must be escaped so the diagram still renders. Task 4 covers it.
- A cycle passing through a symbol of another seam must still mark this seam's members red, and must list the full path. Task 4 covers it.
- About 17,000 WordPress symbols: the build must only make pages for symbols assigned to a seam, and list the unassigned ones on one coverage page. Tasks 6 and 8 cover it.

Content conventions, fixed here:
- `content/wordpress/<seam>/<slug>.mdx` and `content/speedyspec/<seam>/<slug>.mdx` hold hand-written prose for one symbol. Frontmatter `symbol: <id>` is required. On SpeedySpec pages, also `verdict: works-as-wordpress | works-with-differences | breaks | new-in-speedyspec` and `differences: [{ summary: string, break?: string }]`.
- `content/<section>/<seam>/_seam.mdx` holds the seam's introduction; `content/speedyspec/<seam>/_porting.mdx` the porting guide; `_architecture.mdx` the architecture page. Files starting with `_` are never symbol pages.
- Examples render automatically from `seams/<seam>/examples/<symbol folder>/*.php`. An example's heading is its first line comment (`// Change a value…`), which is left out of the code shown. The symbol folder is the slug of the symbol (Task 2).
- Seam ids `porting`, `architecture` and `runtime` are reserved (they are fixed routes under `/speedyspec/`); `SeamFiles` refuses a seam folder with one of those names.
- seam.yaml gains optional fields the pages render: `packages: [string]`, `crates: [string]`, and `dependencies: { <target id>: php | port | rust }` (the SpeedySpec state of a cross-seam dependency, filled in plan 4).

### Task 2: Slugs and the data loader

**Files:** Create `site/src/model/{slug,data}.ts`, `site/test/{slug,data}.test.ts`, fixtures `site/test/fixtures/{generated,seams,content}/` (a hooks seam with `add_filter`, `apply_filters`, `class:WP_Hook` with two methods, `global:wp_filter`, `filter:the_content`, a dynamic `filter:pre_option_{$option}`; one cross-seam edge to an `options` seam; one cycle; one example with results; a WordPress and a SpeedySpec content page for `add_filter`).

**Interfaces:**
- `symbolSlug(id: string): string` and `symbolFromSlug(slug: string, ids: Set<string>): string | undefined`:

  - `class:WP_Hook` → `WP_Hook`; `class:WpOrg\Requests\Exception` → `WpOrg.Requests.Exception`

### Task 3: Verdicts, provenance and views

**Files:** Create `site/src/model/{verdict,views}.ts`, `site/test/{verdict,views}.test.ts`.

**Interfaces:**
- `speedyspecVerdict(id: string, d: GuideData): { verdict: Verdict | 'same-code' | 'modified' | 'removed' | 'unknown'; differences: { summary: string; break?: string }[]; source: 'page' | 'fork' | 'none' }`: a SpeedySpec content page's `verdict` wins; else, in an unported seam, the fork verdict (`same` → `same-code`, `modified`, `removed`); else `unknown`.
- `wordpressProvenance(id: string, d: GuideData): { tier: 'verified' | 'read-from-source' | 'not-documented'; wordpress: string; since?: string; removed?: string }`: `verified` when its WordPress page cites at least one scenario; `read-from-source` when it has a page with only source citations; `not-documented` without a page. `since` and `removed` come from `wordpressHistory`.
- `speedyspecProvenance(id, d): { added: string; removed?: string; native: boolean }`: `added` from `speedyspecHistory` (`unreleased` when absent); `native` when the id is in `runtime`.
- `seamView(seamId: string, section: 'wordpress' | 'speedyspec', d: GuideData): SeamView` with `{ id, name, job, ported, roles: { role: string; members: MemberView[] }[] }`, where `MemberView` is `{ id, kind, name, slug, href, verdict, circular: boolean, methods?: MemberView[] }`. Members are those in `assignment.seamOf` for the seam. Roles come in seam.yaml order. Members in no role go to `other`, sorted by name. Classes carry their methods.
- `symbolView(id: string, section, d): SymbolView` with `{ id, kind, name, signature, seam: SeamView, role, provenance, verdict, edges: { kind: string; label: string; to: { id, name, href, circular } }[], callsInto: { seam: string; symbols: { id, name, href, circular }[] }[], fires: { id, name, href, dynamic: boolean }[], examples: ExampleView[], content: ContentEntry | null, methods?: SymbolView[] }`.
  - `edges` combine seam.yaml edges and the graph's `reads`, `writes`, `calls` and `runs` edges within the seam.
  - `callsInto` comes from `graph.crossSeam`.
  - `fires` is the `fires` edges.
  - `circular` is true when both ends are in one `cycles.components` group.
- `ExampleView` is `{ id, name, title, code, sides: { side, status: 'passed' | 'failed' | 'not-run'; detail?: string }[] }`. `title` is the first line comment, `code` the file without that line. The status comes from the example results.

### Task 4: Mermaid diagrams

**Files:** Create `site/src/model/{mermaid,render-mermaid}.ts`, `site/test/mermaid.test.ts`; modify `site/package.json` (`mermaid-isomorphic`, `rehype-mermaid`, `playwright`) and `astro.config.mjs` (`rehype-mermaid` with `strategy: 'img-svg', dark: true` for MDX code blocks).

**Interfaces:**
- `seamDiagram(view: SeamView, d: GuideData): string`: a `flowchart LR`.
  - Nodes: the seam's functions, classes and globals (not methods, not hooks), labelled with names; globals use the stadium shape. One node per other seam with a cross-seam dependency, labelled with that seam's name.
  - Edges, labelled `calls`, `reads`, `writes`, `undone by`, `alias of`:
    - within the seam: from seam.yaml and the graph (`calls`, `reads`, `writes`)
    - to and from other seams: one edge per direction, labelled with a count (`calls 3`)
    - hook links: dashed (`-.->`)
  - Cycles: `classDef cycle fill:#fde8e8,stroke:#9b1c1c,color:#7f1d1d`. Every node in a cycle component gets `:::cycle` and the label suffix `· circular`. Every edge on a listed cycle path gets a red `linkStyle`.
- `architectureDiagram(seam: SeamFile, crates: CratesFile): string`: a `flowchart TB` of the seam's `packages` and `crates`, and the dependencies between those crates (Task 7's `crates.json`).
- `escapeLabel(text: string): string`: wraps in `"…"` and replaces `"` with `#quot;`, `{` with `#123;`, `}` with `#125;`, `<` with `#lt;`, `>` with `#gt;`. A node id is `n<index>`, never derived from the label.
- `renderMermaid(code: string): Promise<{ light: string; dark: string }>`: SVG strings from `mermaid-isomorphic` (themes `default` and `dark`), cached by the code's sha256 for the build.
