# Search engines demand less, punish inconsistency

As of November 2026, what search engines technically require from a website is small, stable and almost entirely server-side: a crawlable URL that returns a real HTTP 200 with indexable content, plus a short list of signals (title, robots directives, one canonical, accurate sitemaps, hreflang, structured data, preview metadata) that must agree with each other. Google has only three minimum requirements, and its AI Overviews and AI Mode add none: indexed and snippet-eligible is the whole test ([Search technical requirements](https://developers.google.com/search/docs/essentials/technical); [AI features](https://developers.google.com/search/docs/appearance/ai-features)). The engines diverge mainly at the edges: Bing reuses `noarchive` and `nocache` to control Copilot, Yandex and Seznam add their own robots.txt directives, IndexNow reaches every major engine except Google, and AI vendors split their bots into training, search and user-fetch roles with different robots.txt behaviour. Meanwhile Google has spent three years deleting rich results (HowTo, sitelinks search box, seven types in 2025, FAQ in May 2026), so any per-type structured-data generator is volatile. For a WordPress-derived CMS this points to a core API that owns the consistency-critical primitives (head metadata, robots directives, canonical, sitemaps, robots.txt, a small JSON-LD identity graph, Open Graph, hreflang, redirects, a URL-changed event) and treats everything engine-specific or content-type-specific as a registry that plugins fill. Several findings rest only on secondary sources, most importantly the current Bing guideline text, everything about Baidu and Naver, and X Cards; those are marked where they appear. The notes do not audit what the existing codebase already emits, so the tiering at the end describes target scope, not a gap analysis.

## Three hard requirements, and a fixed vocabulary Google actually reads

Google's floor is that Googlebot is not blocked, the page returns HTTP 200, and it has indexable content; meeting this makes a page eligible, never guaranteed ([Search technical requirements](https://developers.google.com/search/docs/essentials/technical)). Everything else is a signal, and the set Google reads is closed. It supports `<title>`, meta description, `robots`/`googlebot` meta and the equivalent `X-Robots-Tag` header, `data-nosnippet`, `rel=canonical`, hreflang, `rel` link qualifiers, viewport, charset, `rating` and `google-site-verification`. It explicitly ignores **meta keywords, the HTML `lang` attribute for language detection, `rel=next/prev`, and `nositelinkssearchbox`** ([Meta tags Google supports](https://developers.google.com/search/docs/crawling-indexing/special-tags)). The robots rule set is `noindex`, `nofollow`, `none`, `nosnippet`, `indexifembedded`, `max-snippet`, `max-image-preview`, `max-video-preview`, `notranslate`, `noimageindex` and `unavailable_after`; `noarchive` and `nocache` are dead for Google, and on conflict the more restrictive rule wins ([Robots meta tag specifications](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)). No title or description length limit is documented; the character counts circulated in the industry are not Google's.

Two interactions in this vocabulary matter for API design. First, robots meta and `X-Robots-Tag` are seen only if the URL is crawled, so a robots.txt disallow silently disables `noindex`, and a disallowed URL can still be indexed ([Robots meta tag specifications](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)). Seznam and Brave state the same rule in their own docs ([Seznam help](https://o-seznam.cz/napoveda/vyhledavani/en/crawling-control/); [Brave Search help](https://search.brave.com/help/brave-search-crawler)). An API that lets one setting disallow and another setting noindex the same URL is building a known trap. Second, Google may skip rendering when it sees `noindex` in the initial HTML or when the status is not 200, and it advises against setting or changing meta tags, canonicals or `data-nosnippet` with JavaScript ([JavaScript SEO basics](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics); [Canonicalization](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)). The only large study of dedicated AI crawlers, a December 2024 log analysis, found none of them executed JavaScript ([Vercel](https://vercel.com/blog/the-rise-of-the-ai-crawler)); it is a single unreplicated study, but it points the same way. Server-rendered head output is the only form every consumer sees, which is exactly what a PHP core API produces.

Canonicalization is signal stacking, not a directive. Permanent redirects and `rel=canonical` are strong signals, sitemap inclusion is weak, HTTPS is preferred, and membership of a reciprocal hreflang cluster counts; a `rel=canonical` combined with `hreflang`, `lang`, `media` or `type` is ignored ([Canonicalization](https://developers.google.com/search/docs/crawling-indexing/consolidate-duplicate-urls)). The practical requirement is one absolute, self-referential canonical per indexable page, with sitemap entries, hreflang targets and internal links all using that same URL. Paginated archives each keep their own canonical instead of pointing at page one ([Pagination](https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading)). Redirects follow the same logic: **301 and 308 make the target canonical, 302/303/307 do not**, Googlebot follows up to 10 hops, and site-move redirects should stay for at least a year ([Redirects](https://developers.google.com/search/docs/crawling-indexing/301-redirects); [Site moves](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)). Google treats 404 and 410 alike, treats 429 and 5xx as overload signals that slow crawling, and flags empty or error-looking 200 pages as soft 404s ([HTTP status codes](https://developers.google.com/search/docs/crawling-indexing/http-network-errors)). The notes found no Google statement on trailing slashes; the advice to pick one form and redirect the other is an inference from general URL rules, not a cited requirement.

Sitemaps and robots.txt have equally tight specs. Google reads only `user-agent`, `allow`, `disallow` and `sitemap` in robots.txt, caps the file at 500 KiB, and ignores `crawl-delay` ([How Google interprets robots.txt](https://developers.google.com/search/docs/crawling-indexing/robots/robots_txt)). Sitemaps are capped at **50,000 URLs or 50 MB uncompressed**, should list only canonical URLs, and `priority` and `changefreq` are ignored; `lastmod` is used only when consistently accurate ([Build and submit a sitemap](https://developers.google.com/search/docs/crawling-indexing/sitemaps/build-sitemap)). Bing says the same from the other side: it "largely disregards" `changefreq` and `priority`, discards `lastmod` values that always equal the current date, and has moved crawl scheduling toward `lastmod` ([Bing Webmaster Blog](https://blogs.bing.com/webmaster/february-2023/The-Importance-of-Setting-the-lastmod-Tag-in-Your-Sitemap)). Google's sitemap ping endpoint is gone ([Google blog](https://developers.google.com/search/blog/2023/06/sitemaps-lastmod-ping)). The image sitemap extension has shrunk to `<image:loc>` only, and news sitemaps cover the last two days with at most 1,000 entries ([Image sitemaps](https://developers.google.com/search/docs/crawling-indexing/sitemaps/image-sitemaps); [News sitemaps](https://developers.google.com/search/docs/crawling-indexing/sitemaps/news-sitemap)).

Ranking eligibility adds little that a metadata API controls. Core Web Vitals (LCP within 2.5 s, INP at or under 200 ms, CLS at or under 0.1, at the 75th percentile) are the only page-experience aspect Google says its ranking systems use, and there is no single page-experience signal ([Core Web Vitals](https://developers.google.com/search/docs/appearance/core-web-vitals); [Page experience](https://developers.google.com/search/docs/appearance/page-experience)). Mobile-first indexing has been complete since October 2023 and requires identical robots meta, titles, structured data and primary content on mobile and desktop ([Mobile-first indexing best practices](https://developers.google.com/search/docs/crawling-indexing/mobile/mobile-sites-mobile-first-indexing)). The spam policies a CMS can influence are narrower still: qualify paid and user-generated links with `rel="sponsored"`, `rel="ugc"` or `nofollow`, control user-generated spam, and since April 2026 avoid back-button hijacking ([Spam policies](https://developers.google.com/search/docs/essentials/spam-policies); [Changelog](https://developers.google.com/search/updates)). The back-button policy was seen only as a changelog line; its full text was not retrieved.

## Bing, Yandex and the smaller engines diverge at the edges

Supporting Bing covers most Western alternatives. DuckDuckGo says its links are "largely sourced from Bing" ([DuckDuckGo Help](https://duckduckgo.com/duckduckgo-help-pages/results/sources)), and secondary lists put Yahoo and Ecosia on Bing as well, with Ecosia and Qwant building their own index, Staan, since August 2025 ([Search Engine World](https://www.searchengineworld.com/the-big-search-engine-list-who-indexes-what); [TechCrunch](https://techcrunch.com/2025/08/06/qwant-and-ecosia-debut-staan-a-european-search-index-that-aims-to-take-on-big-tech)). Brave runs an independent index but, by its own help page, advertises no distinct user agent, crawls only what Googlebot may crawl, and requires `noindex` rather than robots.txt for removal ([Brave Search help](https://search.brave.com/help/brave-search-crawler)). A third-party directory lists a "BraveBot/1.0" agent, which contradicts Brave's own statement; Brave's page should win ([Dark Visitors](https://darkvisitors.com/agents/bravebot)). Applebot likewise falls back to Googlebot rules when it is not named ([Apple support](https://support.apple.com/en-us/119829)). Googlebot rules therefore have side effects on at least two other crawlers, and none of DuckDuckGo, Yahoo, Ecosia or Brave needs any engine-specific output.

The source quality for Bing needs stating plainly. **Bing's Webmaster Guidelines and help pages are JavaScript-rendered and could not be read directly**; what follows about the February 2026 rewrite comes from trade press. According to that coverage, Bing reorganized the guidelines around eligibility for Copilot grounding, and now says `NOARCHIVE` prevents content being used in Copilot responses and grounding, while `NOCACHE` limits Copilot to URL, title and snippet ([Search Engine Journal](https://www.searchenginejournal.com/bing-adds-geo-to-official-guidelines-expands-ai-abuse-definitions/568442/); [Search Engine Roundtable](https://www.seroundtable.com/bing-webmaster-guidelines-updated-41002.html)). What is confirmed from Bing's own blog is narrower: Bing supports `noindex`, `nosnippet`, `max-snippet`, `max-image-preview`, `max-video-preview`, and since October 2025 `data-nosnippet` on any HTML element ([Bing Webmaster Blog](https://blogs.bing.com/webmaster/October-2025/Bing-Introduces-Support-for-the-data-nosnippet-HTML-Attribute)). Google accepts `data-nosnippet` only on `span`, `div` and `section`, so those three elements are the portable subset. Bing's `Crawl-delay` support, its verification file name and its canonical and redirect guidance also rest on secondary sources or the researchers' memory. The claim that hreflang is "a far weaker signal than content-language at Bing" is a 2020 statement by a Bing employee with no later restatement found ([Search Engine Roundtable](https://www.seroundtable.com/bing-hreflang-weak-signal-30099.html)), and it sits awkwardly beside Google's statement that it ignores the `lang` attribute. Emitting both `<html lang>` and hreflang costs nothing and satisfies both.

robots.txt is where the engines disagree most, and the disagreements are engine-scoped directives that a strict four-field model cannot express.

| Directive | Google | Bing | Yandex | Seznam | AI vendors |
|---|---|---|---|---|---|
| `Sitemap` | Yes | Yes | Yes | Yes | n/a |
| `Crawl-delay` | Ignored | Honored (secondary source only) | Ignored since Feb 2018 | Third-party claim, not in Seznam docs | Anthropic and You.com honor; Apple and Amazon do not |
| `Clean-param` | No | No | Yes | No | No |
| `Request-rate` | No | No | No | Yes | No |
| `Host` | Never | No | Deprecated 2018 (secondary) | No | No |

Sources: [Google](https://developers.google.com/search/docs/crawling-indexing/robots/robots_txt); [WebProNews](https://www.webpronews.com/bing-details-how-to-control-bingbot-crawling-behavior); [Yandex robots.txt](https://yandex.com/support/webmaster/en/controlling-robot/robots-txt); [Yandex Clean-param](https://yandex.com/support/webmaster/en/robot-workings/clean-param); [Seznam help](https://o-seznam.cz/napoveda/vyhledavani/en/crawling-control/); [Anthropic support](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler); [Apple support](https://support.apple.com/en-us/119829); [Amazonbot](https://developer.amazon.com/amazonbot).

Two Yandex rules constrain core design directly. A `User-agent: Yandex` group makes Yandex ignore the `*` group entirely ([Yandex Clean-param](https://yandex.com/support/webmaster/en/robot-workings/clean-param)), which matches Google's most-specific-group behaviour, so a builder that adds a named group must copy the general rules into it. And Yandex accepts hreflang only as `<link>` elements in `<head>`, having dropped sitemap-based language annotations ([Yandex Webmaster](https://yandex.com/support/webmaster/en/yandex-indexing/locale-pages)), whereas Google treats head, HTTP header and sitemap as equivalent and requires reciprocal return links, fully qualified URLs and `x-default` for fallbacks ([Localized versions](https://developers.google.com/search/docs/specialty/international/localized-versions)). HTML head output is the one method that works for both. Yandex Turbo pages were discontinued in April 2025 and need no support ([Yandex Webmaster](https://yandex.com/support/webmaster/en/service/about)).

IndexNow is the one push mechanism with broad reach. A single GET, or a JSON POST of up to 10,000 URLs to `api.indexnow.org`, authenticated by an 8-to-128-character key served at `/{key}.txt`, is shared among Bing, Yandex, Seznam, Naver, Yep, the Internet Archive and Amazonbot ([IndexNow documentation](https://www.indexnow.org/documentation); [searchengines.json](https://www.indexnow.org/searchengines.json)). The protocol asks for new, updated, deleted and redirected URLs only, a wait of at least five minutes before resubmitting the same URL, and back-off on 429; each subdomain needs its own key ([IndexNow FAQ](https://www.indexnow.org/faq)). Bing calls adoption "highly recommended" ([Bing Webmaster Blog](https://blogs.bing.com/webmaster/february-2023/The-Importance-of-Setting-the-lastmod-Tag-in-Your-Sitemap)). **Google does not participate**: it said in 2021 it would test the protocol and no adoption has been reported since, though that conclusion rests on absence of evidence and one secondary article ([Search Engine Roundtable](https://www.seroundtable.com/google-indexnow-32396.html)). Microsoft's own WordPress plugin has over 100,000 installs, and Cloudflare can send IndexNow signals at the CDN layer, so double submission is a real possibility ([WordPress.org](https://wordpress.org/plugins/indexnow/); [Cloudflare docs](https://developers.cloudflare.com/cache/advanced-configuration/crawler-hints/)).

Baidu and Naver are the weakest part of the evidence. **No Baidu primary documentation was read.** Vendor guides and community tutorials describe a proprietary push API (plain-text POST to `data.zz.baidu.com/urls` with a site token), an `applicable-device` meta tag, weak JavaScript rendering and partial canonical support ([x-cmd](https://x-cmd.com/seo/baidu); [Chinafy](https://www.chinafy.com/blog/technical-seo-checklist-for-baidu); [Dragon Metrics](https://www.dragonmetrics.com/how-to-succeed-in-baidu-mobile-seo/)); quotas and tag names are unconfirmed. Naver's participation in IndexNow is confirmed by the registry file, but its verification tag, crawler behaviour and RSS submission come from secondary guides only ([inblog](https://inblog.ai/docs/seo-tutorial-domain-setup/registering-with-naver-search-advisor)). Site verification follows one pattern everywhere it exists: a `<meta name="…" content="token">` on the home page, with file and DNS alternatives. Only Yandex's tag name was confirmed from primary documentation ([Yandex Webmaster](https://yandex.com/support/webmaster/en/service/rights)); Bing's `msvalidate.01` comes from a plugin vendor's docs, and the Baidu and Seznam names are from memory. Brave and DuckDuckGo have no verification at all.

## Rich results shrank to identity, commerce and media

Google's Search Gallery lists 25 features in November 2026, and the list of what left is longer than what arrived ([Search Gallery](https://developers.google.com/search/docs/appearance/structured-data/search-gallery)). HowTo went in September 2023 ([Search Central blog](https://developers.google.com/search/blog/2023/08/howto-faq-changes)). Book actions, course info, ClaimReview, estimated salary, learning video, special announcement and vehicle listing were phased out from June 2025 ([Search Central blog](https://developers.google.com/search/blog/2025/06/simplifying-search-results)). Practice problems followed in January 2026, and **FAQ rich results stopped appearing on 7 May 2026**, with documentation removed on 15 June ([Changelog](https://developers.google.com/search/updates)). Breadcrumb rich results have been desktop-only since January 2025. Google says leftover markup is harmless and removals do not affect ranking, so there is no need to strip old markup, only to stop building for it.

On the sitelinks search box, the two notes give dates that look inconsistent but describe different events. The structured-data note cites Google's blog for the feature leaving Search on **21 November 2024** ([Search Central blog](https://developers.google.com/search/blog/2024/10/sitelinks-search-box)); the Google note cites the changelog entry of **29 November 2024**, which records the documentation being removed and the `nositelinkssearchbox` rule archived ([Changelog](https://developers.google.com/search/updates)). The Google note's shorthand that the feature was "removed 2024-11-29" is the documentation date; the feature itself ended eight days earlier. Either way `SearchAction` markup has no remaining Google function, while `WebSite` markup lives on for site names.

What survives divides cleanly by how much the CMS knows without asking. `WebSite` on the home page needs only `name` and `url`, and is the strongest site-name signal, supported at domain and subdomain level only ([Site names](https://developers.google.com/search/docs/appearance/site-names)). `Organization` and `Article`/`BlogPosting` have no required properties at all, only recommended ones such as `headline`, `image`, `datePublished`, `dateModified` and `author` with a `url` ([Organization](https://developers.google.com/search/docs/appearance/structured-data/organization); [Article](https://developers.google.com/search/docs/appearance/structured-data/article)). `BreadcrumbList` needs two or more items, and `ProfilePage` needs a `mainEntity` with a name ([Breadcrumb](https://developers.google.com/search/docs/appearance/structured-data/breadcrumb); [Profile page](https://developers.google.com/search/docs/appearance/structured-data/profile-page)). A CMS can generate all of these from data it already holds. By contrast, merchant listings require `name`, `image` and an `Offer` with a positive `price` and `priceCurrency`; events require a physical `location`; recipes, job postings, local businesses and videos each require fields that only a content-type plugin has ([Merchant listing](https://developers.google.com/search/docs/appearance/structured-data/merchant-listing); [Event](https://developers.google.com/search/docs/appearance/structured-data/event)). Google recommends JSON-LD, says items that belong together can share an `@id`, and wants the same markup on duplicate pages, not only the canonical ([Structured data policies](https://developers.google.com/search/docs/appearance/structured-data/sd-policies)). Yoast's design, a single `@graph` of flat pieces cross-referenced by stable `@id`s with filters at piece-list, per-piece and whole-graph level, is the mature reference for an extensible implementation ([Yoast Schema API](https://developer.yoast.com/features/schema/api/); [Yoast technology and approach](https://developer.yoast.com/features/schema/technology-approach/)).

Outside Google the picture is thinner. Yandex documents using JSON-LD for breadcrumbs and for Q&A in mobile results ([Yandex Webmaster](https://yandex.ru/support/webmaster/en/json-ld/about)), so question-and-answer markup keeps some value there after Google's FAQ removal. Bing's current list of supported types could not be read; the latest primary statement is a 2018 post announcing JSON-LD support alongside Microdata, RDFa, Microformats and Open Graph ([Bing Webmaster Blog](https://blogs.bing.com/webmaster/august-2018/Introducing-JSON-LD-Support-in-Bing-Webmaster-Tools)). Baidu's JSON-LD support is unknown.

Preview metadata does double duty. Open Graph formally requires `og:title`, `og:type`, `og:image` and `og:url` ([ogp.me](https://ogp.me/)), but Google also reads `og:title` as a title-link source, `og:site_name` as a site-name signal and `og:image` as the preferred Discover image ([Title links](https://developers.google.com/search/docs/appearance/title-link); [Discover](https://developers.google.com/search/docs/appearance/google-discover)). Discover needs images at least **1200 px wide enabled by `max-image-preview:large`**, and Facebook and LinkedIn both recommend roughly 1200 by 630 at a 1.91:1 ratio ([Meta sharing docs](https://developers.facebook.com/docs/sharing/webmasters/images/); [LinkedIn Help](https://www.linkedin.com/help/linkedin/answer/a521928)). One large featured image with declared dimensions therefore serves search and social at once. Size limits for Slack, Discord, WhatsApp and iMessage come only from secondary guides that contradict each other. **X Cards cannot be verified from a primary source**: X's developer pages returned HTTP 402, and current guidance comes from a plugin vendor's knowledge base, which reports that the `twitter:*` names still work, that X has removed much of its card documentation, and that `twitter:site` and `twitter:creator` may no longer affect the preview ([The SEO Framework KB](https://kb.theseoframework.com/kb/twitter-cards-and-x-sharing/)). Mastodon's `fediverse:creator` tag and Pinterest's reuse of Open Graph and schema.org are documented by those platforms ([Mastodon blog](https://blog.joinmastodon.org/2024/07/highlighting-journalism-on-mastodon/); [Pinterest developer docs](https://developers.pinterest.com/docs/web-features/rich-pins-overview/)). Bluesky and Threads behaviour was not sourced.

## AI engines add bot roles, not new markup

No answer engine documents a markup requirement. Google states there are "no additional requirements" for AI Overviews or AI Mode and no special schema or AI text files ([AI features](https://developers.google.com/search/docs/appearance/ai-features)). Its generative-AI optimization guide says llms.txt is not used by Google Search ([Optimizing for generative AI features](https://developers.google.com/search/docs/fundamentals/ai-optimization-guide)). The notes differ slightly on how well this is sourced: the Google note read the guide and changelog directly, while the AI note had it only through trade press; the direct reading stands. There is one counter-signal inside Google, reported secondhand: Lighthouse 13.3's experimental agentic-browsing audit checks for llms.txt, but it targets browser agents, not ranking or citation ([Search Engine Journal](https://www.searchenginejournal.com/googles-llms-txt-guidance-depends-on-which-product-you-ask/575431/)). Usage data points the same way. Summaries of an Ahrefs study of 137,210 domains report that 97% of llms.txt files received zero requests in May 2026, and Common Crawl found about two-thirds of the files it examined were plugin-generated ([Optimizely](https://www.optimizely.com/field-notes/articles/does-llms-txt-work/); [Common Crawl blog](https://commoncrawl.org/blog/a-content-analysis-of-llms-txt-files-from-the-july-2026-crawl-archive)). The file is spreading because plugins write it, not because crawlers read it.

What the AI vendors do document is access control, and its shape is consistent. Each splits its agents into a training crawler, a search-index crawler and a user-triggered fetcher. Blocking `GPTBot`, `ClaudeBot`, `Google-Extended`, `Applebot-Extended`, `CCBot` or `meta-externalagent` withholds content from training with no documented visibility cost, whereas blocking `OAI-SearchBot`, `Claude-SearchBot`, `PerplexityBot` or `meta-webindexer` removes the site from that product's answers ([OpenAI bots docs](https://developers.openai.com/api/docs/bots); [Anthropic support](https://support.claude.com/en/articles/8896518-does-anthropic-crawl-data-from-the-web-and-how-can-site-owners-block-the-crawler); [Perplexity docs](https://docs.perplexity.ai/guides/bots); [Meta web crawlers](https://developers.facebook.com/docs/sharing/webmasters/web-crawlers/)). The user-triggered fetchers are a different matter: OpenAI says robots.txt rules "may not apply" to `ChatGPT-User`, Perplexity says `Perplexity-User` "generally ignores" them, and Meta and Amazon make similar statements. **robots.txt cannot reliably stop user-initiated fetches**; enforcement belongs to the host or CDN using published IP lists. `Google-Extended` and `Applebot-Extended` are control tokens that never crawl, and `Google-Extended` does not govern AI Overviews or AI Mode, which run on Googlebot's index ([Google common crawlers](https://developers.google.com/crawling/docs/crawlers-fetchers/google-common-crawlers)).

Page-level control over AI answers reuses the old preview directives, with meanings that now differ by vendor. For Google, `nosnippet`, `max-snippet` and `data-nosnippet` bound what AI Overviews and AI Mode may use, at the cost of the classic snippet; there is no page-level AI-only switch ([Robots meta tag specifications](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag)). The site-level switch arrived in 2026 as a Search Console setting, announced 3 June and rolled out worldwide by 31 August, which Google says is not a ranking signal outside those features ([Google blog](https://blog.google/products-and-platforms/products/search/new-controls-website-owners)). It lives entirely outside the site's output; its option names come from secondary coverage, and no on-site or API equivalent is documented. `noarchive` now carries three meanings: nothing for Google, no Copilot use for Bing (secondary source), and "do not use the page for model training" for Amazon ([Amazonbot](https://developer.amazon.com/amazonbot)). That alone argues against core hard-coding the semantics of any directive.

The standards meant to replace this patchwork are unsettled. The IETF AIPREF drafts define a `Content-Usage` HTTP header and robots.txt rule, with no RFC published and the working group's August 2026 milestone missed ([draft-ietf-aipref-attach-05](https://www.ietf.org/archive/id/draft-ietf-aipref-attach-05.html)). Google says it intends to support a training-preference signal in early 2027, written as `user-agent: __usage_ai-training`, a pseudo-agent syntax that does not match the `Content-Usage:` rule in the working-group draft ([Google common crawlers](https://developers.google.com/crawling/docs/crawlers-fetchers/google-common-crawlers)). That discrepancy is unresolved in the notes, and the Google wording was seen only in summary. Cloudflare's `Content-Signal:` line sits on more than 3.8 million domains by Cloudflare's own count, and RSL adds a `License:` line; neither has a documented AI vendor honoring it ([Cloudflare blog](https://blog.cloudflare.com/content-signals-policy/); [rslstandard.org](https://rslstandard.org/)). Four syntaxes for one idea, none ratified, means core should model the intent (search, AI input, AI training) and leave serialization open.

Evidence on what earns citations is weak beyond access. The vendor-documented levers are not blocking the search-role bot, being indexed and snippet-eligible on Google, and, per trade-press reports of Bing's guidelines, avoiding `noarchive`/`nocache` and writing single-topic pages. Freshness and structured-data effects rest on correlational industry studies with conflicting magnitudes, read only through summaries, and Google states no special schema is needed. The honest position is that accurate `dateModified` and `lastmod`, server-rendered content and correct robots output are the AI-visibility features, and they are the same features classic search already requires.

## Conclusion: what belongs in core, what plugins extend, what to skip

The evidence sorts capabilities by one test: does the requirement hold across engines, depend only on data the CMS already owns, and break when two components disagree? If yes, it belongs in core. If it is engine-specific, content-type-specific or still changing, core should expose a registry and stop. If no engine reads it, it should not be built.

### Must be in the core API

**Head metadata registry and document title.** Every engine reads `<title>` and meta description, and Google rewrites titles that are missing, boilerplate or mismatched ([Title links](https://developers.google.com/search/docs/appearance/title-link)). The registry must accept both `name` and `property` attributes, since Open Graph uses `property` and X, Mastodon and verification tags use `name`. It should emit no meta keywords and impose no length limits, because none is documented.

**Robots directives as one resolved value per response, emitted as meta and `X-Robots-Tag`.** The directive list must be open-ended, with `noindex`, `nofollow`, `nosnippet`, `max-snippet`, `max-image-preview`, `max-video-preview`, `noarchive` and `nocache` as distinct values, because Bing and Amazon give the last two live meanings that Google does not. The header form is needed for attachments, PDFs and feeds. `max-image-preview:large` is the right default for public content because Discover depends on it. Core should also refuse or warn when a URL is both disallowed in robots.txt and marked `noindex`, since four engines document that the disallow hides the directive.

**One canonical URL service feeding every consumer.** A single resolver should supply `rel=canonical`, `og:url`, sitemap `<loc>`, hreflang targets and the structured-data `url`, always absolute and HTTPS, with paginated views self-canonical. This is the clearest case for core: Google treats disagreement between these as weakened signals, and separate plugins cannot keep them aligned.

**robots.txt builder with per-agent groups and free-form lines.** The model needs user-agent groups, `Allow`, `Disallow`, `Sitemap`, and arbitrary extra directives inside and outside groups. That one design decision accommodates `Clean-param`, `Request-rate`, `Crawl-delay`, `Content-Signal:`, `Content-Usage:`, `License:` and Google's planned pseudo-agent without core endorsing any. It must copy general rules into any named group it creates, and stay under 500 KiB.

**XML sitemaps with honest `lastmod`.** Split at 50,000 URLs, list only canonical indexable URLs, advertise via robots.txt, and derive `lastmod` from real content modification. Google and Bing both discard inaccurate dates and both ignore `priority` and `changefreq`, so core should omit those two. Image entries need only `<image:loc>`.

**Redirects and status codes.** A redirect store defaulting to 301 or 308 for slug and URL changes, retained long term, plus correct 404 or 410 for missing content and 503 for maintenance. Permanent redirects are Google's strongest canonical signal, and a 200 on an error page becomes a soft 404.

**A minimal JSON-LD identity graph with stable `@id`s.** Core should emit `WebSite` on the home page, `Organization` or `Person`, `BreadcrumbList`, `Article`/`BlogPosting` on posts and `ProfilePage` on author archives, in one server-rendered `@graph`. These types have zero or trivial required properties and use only data core holds, and the documented `@id`s become the public contract that lets plugins attach richer nodes.

**Open Graph baseline.** `og:title`, `og:type`, `og:url`, `og:description`, `og:site_name`, `og:locale`, `og:image` with width, height and alt, plus `article:*` times on posts, and a registered image size near 1200 by 630. Google, Bing, Facebook, LinkedIn and Pinterest all consume these, and X falls back to them.

**hreflang as a core primitive, populated by plugins.** Core should own the output rules: `<link>` elements in the head (the only method both Google and Yandex accept), reciprocal sets, absolute URLs, `x-default`, valid codes. The translation relationships themselves come from a multilingual plugin through a provider interface.

**A URL-changed event and a link-qualifier default.** One event for publish, update, delete and redirect, carrying canonical URLs and skipping noindex content, is the hook every push protocol needs. Comment and other user-generated links should default to `rel="ugc"`, which Google's spam policy places on the site owner.

### Should be an extension point for plugins

**IndexNow and other push protocols.** The protocol is small and reaches Bing, Yandex, Seznam and Naver in one call, so a bundled adapter is defensible. It should still sit behind the URL-changed event as a replaceable sender: Google does not consume it, Baidu uses a different API known only from secondary sources, and Cloudflare or an existing plugin may already be submitting. Core's job is the event, a route that can serve `/{key}.txt`, and a filter so only one sender fires.

**Site verification.** A registry of meta name and content pairs, plus the ability to serve small root-level files, covers every console. Core should not hard-code engine fields, because only Yandex's tag name was confirmed from primary documentation.

**AI crawler controls.** Core should ship the mechanism (the robots.txt builder, per-response headers, robots directives) and a neutral three-purpose model of search, AI input and AI training. The agent-token list and its role grouping should be filterable data, not constants: new tokens appeared repeatedly in 2025 and 2026, the standards are unratified, and user-triggered fetchers ignore robots.txt regardless. Google's site-level AI opt-out is a Search Console setting that no CMS output can reach.

**Content-type structured data.** Product, Offer, Review, Event, Recipe, JobPosting, LocalBusiness, VideoObject, QAPage and DiscussionForumPosting need plugin-held data and track a gallery that Google has cut repeatedly. A piece registry with needs-check, generate and filter layers, in Yoast's pattern, lets these come and go without core changes.

**Network-specific social tags.** `twitter:card` and `twitter:image:alt`, `fediverse:creator`, and product Open Graph tags fit the meta registry. X's behaviour is unverified from primary sources, which is reason enough to keep it out of core's guarantees.

**News and video sitemaps, engine-specific tags and robots.txt lines.** News sitemaps apply to a narrow set of publishers; Baidu's `applicable-device`, Yandex's `Clean-param` and Seznam's `Request-rate` are single-engine. A sitemap provider interface and the free-form builders above are sufficient.

**Core Web Vitals.** The thresholds are a ranking input, but they are determined by themes, images and scripts. The SEO API's contribution is to add no client-side work and to expose image dimensions; measurement and optimization belong elsewhere.

### Not worth building

**Meta keywords, `rel=next/prev`, sitemap `priority` and `changefreq`, and sitemap pings.** Google ignores all of them, Bing disregards the sitemap fields, and the ping endpoint returns 404.

**`SearchAction` sitelinks search box, FAQ and HowTo rich-result generators.** Google removed the features in November 2024, May 2026 and September 2023. Existing markup is harmless, and Yandex's Q&A use is a plugin-level concern.

**`Host:` and Yandex Turbo output, AMP-specific plumbing, dynamic rendering.** Yandex dropped the first two, Google removed AMP viewer and cache references in July 2026, and Google has called dynamic rendering a deprecated workaround since February 2024.

**llms.txt in core.** Google says it is not used, log studies show AI crawlers almost never request it, and most existing files are plugin artifacts. A plugin can generate it from sitemap data for the documentation sites where coding agents do fetch it.

**Core-side enforcement against AI fetchers, and WebMCP or NLWeb endpoints in the SEO layer.** Blocking by user agent and IP is host and CDN work that Cloudflare already performs by default for many sites. The agent protocols are early drafts with no documented role in discovery or citation, and belong with the project's agent and abilities work, not with SEO.

The pattern across all three tiers is that the durable part of SEO is agreement between outputs, and the perishable part is every engine's list of names: rich-result types, bot tokens, verification tags, preference syntaxes. A core API built around a canonical resolver, open registries and one change event will absorb the next round of deprecations without modification. Before implementation, three items deserve a direct re-read in a browser because the notes could not confirm them: the live Bing Webmaster Guidelines text on `noarchive` and `nocache`, Google's exact AIPREF syntax and date, and X's current card requirements.
